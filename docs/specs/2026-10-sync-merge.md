## 1. 需求（用戶）

- 目的：現時 `/api/sync`（`worker/worker.js` 的 `mergeCellars()`）和前端 `db.js` 的 `syncToCloudKV()` 以「整支酒」為單位，`updatedAt` 較新者全勝，而 `updatedAt` 來自手機時鐘。因此：
  1. 兩部機各自改同一支酒的不同地方（例如手機 A 加品鑑、手機 B 改狀態為「已開」），後同步的一部會把另一部的改動整個蓋走。
  2. 手機時鐘不準（快或慢幾分鐘甚至幾日）時，較舊的改動可能勝出。
  3. 刪了的酒可能復活：(a) 刪除時間（墓碑）比另一部機的修改時間早，酒就會留下；(b) `saveBottleToDB()` 每次儲存都會清走該酒的刪除記錄，如果畫面上還留著已刪酒款的舊物件（例如另一部機刪了，這部機詳情頁仍開著並按了收藏），儲存後酒會復活並蓋過刪除。
  4. `imageData` 是 `image` 的重複 base64 副本：相片上載雲端後 `image` 會變成網址，但 `imageData` 仍然是整張相的 base64，每次同步都整份送出和寫入 KV，令同步慢、耗流量，並令單一用戶記錄更接近 KV 上限（現時 24MB 會回 `CELLAR_TOO_LARGE`）。
- 使用者：同一帳號用多於一部裝置（手機 + 平板／電腦，或換手機期間）的用戶；單一裝置用戶主要受惠於同步變快。
- 範圍內：
  1. 改為逐欄位合併：同一支酒不同欄位的改動可以同時保留。
  2. 品鑑紀錄 `tastings[]` 按每條紀錄的 `id` 合併，兩部機各自新增的品鑑都保留；刪除品鑑要有記錄，不會復活。
  3. 時間戳不再單靠手機時鐘（混合邏輯時鐘 + 伺服器限制未來時間，見 3.2）。
  4. 刪除規則清楚：刪除後不會因舊資料或時鐘問題復活。
  5. 停止同步 `imageData`；新酒款不再寫 `imageData`；雲端和本機舊資料清理。
  6. 舊版 App（用戶手機仍是舊 cache）送來的資料仍然可以正確合併，不會弄壞雲端資料。
- 範圍外（這次不做）：
  - 即時推送（另一部機改動後即時更新畫面）：仍然在開 App、儲存後或手動同步時同步。
  - 改為只送「有改動的酒」（增量同步）：見 3.5，可以作為之後的優化。
  - 分享酒窖、探索池的資料格式。
  - 配額計數（另一份規格 `2026-10-quota-durable-object.md`）。
- 參考：混合邏輯時鐘（Hybrid Logical Clock, HLC）；逐欄位「最後寫入者勝」（LWW register）。

## 3. 設計（ChatGPT Go）

> 這一節先由 Claude 起草技術方案。ChatGPT Go 如有意見，原文加在本節末尾。

### 3.1 方案選擇

| 方案 | 做法 | 解決「蓋走對方改動」 | 解決「時鐘不準」 | 解決「復活」 | 成本 |
|---|---|---|---|---|---|
| A. 整支酒 LWW，改用伺服器時間 | 伺服器收到時蓋時間 | 否 | 部分（離線改動按收到時間排序，不是改動時間） | 部分 | 低 |
| **B. 逐欄位 LWW + 混合邏輯時鐘（建議）** | 每個欄位記錄改動時間；品鑑按 id 合併；墓碑記錄刪除 | 是 | 是（HLC + 伺服器限制未來時間） | 是 | 中 |
| C. 版本號 + 三方合併 | 伺服器存每個版本，按共同祖先合併 | 是 | 是 | 是 | 高：要保存歷史版本，資料量大 |
| D. CRDT 函式庫（Automerge／Yjs） | 引入函式庫 | 是 | 是 | 是 | 高：專案無 build step，函式庫體積大，資料格式全換 |

建議方案 B。

### 3.2 資料格式

- 每支酒加 `_f`：`{ 欄位名: 時間戳 }`，記錄每個頂層欄位最後改動時間。合併時逐欄位取時間戳較大者；時間戳相同時以固定規則（裝置 id 字典序）決定，保證兩邊結果一樣。
- 合併的欄位：`status`、`buy`、`personalRating`、`isFavorite`、`tags`、`identification`、`scan`、`image`，以及其他頂層欄位（整個值作一個單位）。`id`、`addedAt` 不變。
- `tastings[]`：按品鑑 `id` 合併，每條品鑑自己有時間戳；刪除品鑑記錄在 `_td: { 品鑑id: 時間戳 }`。
- 時間戳：混合邏輯時鐘（HLC）＝ 本機時間與「見過的最大時間戳」取較大者再加計數，確保在同一部機上永遠遞增，並且在收到別部機較新的時間後，本機之後的改動一定排在它之後。
- 伺服器限制：任何時間戳大於伺服器時間 + 5 分鐘，一律壓到伺服器時間（防止時鐘調快的裝置永遠勝出）。
- 儲存時前端比較新舊物件，只為真正改了的欄位更新 `_f`，不再整支酒更新 `updatedAt`（`updatedAt` 保留給舊版 App 使用）。

### 3.3 刪除規則

- 刪除酒款寫墓碑 `deleted[id]`，**刪除優先**：只要有墓碑，該 id 的酒一律不再出現，不再比較修改時間（酒款 id 是隨機產生，重新加入一定是新 id）。
- `saveBottleToDB()` 不再清除墓碑；儲存一支已刪除的酒時不寫入，並通知畫面（AC7）。
- 實作前要檢查 `app.js` 有沒有流程會刻意重用舊 id（例如願望清單轉入酒窖）；如有，改為產生新 id。
- 墓碑不會自動清除（每支只佔約 30 bytes）。

### 3.4 `imageData` 處理

- 前端：新酒款不再寫 `imageData`（`app.js` 約第 3395、3679 行）；同步送出前去掉 `imageData`；本機讀取時如只有 `imageData` 沒有 `image`，把它搬到 `image`，交給現有相片上載流程轉為雲端網址。
- 伺服器：合併時同樣處理（只有 `imageData` 就搬到 `image`，否則刪除），回覆和儲存都不含 `imageData`。
- `bottleImage()` 保留讀 `imageData` 作後備，直至舊資料清理完。

### 3.5 未決定事項

1. **同一支酒在一部機被刪、另一部機同時被修改，保留還是刪除？** 建議：刪除優先（3.3）。代價是：如果用戶在另一部機離線編輯一支已在別處刪除的酒，該編輯會遺失。
   - **用戶決定（2026-10-17）：刪除優先。**
2. **同時同步造成的丟失（AC13）要不要這次處理？** 現時雲端每個用戶是一個 KV 值，兩部機同時同步時，後寫的會蓋走先寫的合併結果；由於本機仍保留資料，下次同步通常會補回，但並不保證。徹底解決要把每個用戶的合併放進 Durable Object（每用戶一個，排隊處理），可以沿用另一份規格建立的 Durable Object。建議：一併處理，並在配額規格完成後才實作本規格。
   - **用戶決定（2026-10-17）：一併處理（AC13 按原文）；配額規格完成後才實作。**
3. **增量同步**：現時每次同步送出整個酒窖。改為只送有改動的酒可再減少流量，但要多記錄「上次同步位置」。建議：這次不做，先完成 `imageData` 清理（已大幅減少資料量）。
   - **用戶決定（2026-10-17）：這次不做。**

### 資料遷移與回退風險（實作時必須處理）

| 資料 | 風險 | 處理方法 |
|---|---|---|
| 雲端舊格式酒窖（沒有 `_f`） | 欄位時間戳缺失，合併時不知道哪邊較新 | 把每個欄位的時間戳視為該酒的 `updatedAt`（或 `addedAt`），並先經過「不超過伺服器時間 + 5 分鐘」限制；第一次寫回時補上 `_f`（AC9） |
| 舊版 App 仍在用戶手機（sw cache） | 送來的酒沒有 `_f`，並可能帶 `imageData` 和整支酒的新 `updatedAt` | 伺服器把沒有 `_f` 的酒當作「所有欄位在 `updatedAt` 時改動」，再與雲端逐欄位合併；去掉 `imageData`。代價：舊版 App 一次儲存會令所有欄位都視為新改動，仍可能蓋走別部機的改動，直至該機更新到新版（AC8） |
| 舊版 App 收到新格式回覆 | 舊版看不懂 `_f`、`_td` | 新增欄位只是附加，舊版會照樣保存並送回，不影響顯示；回覆仍保留 `updatedAt`，舊版比較邏輯照常運作 |
| 只有 `imageData` 的舊酒款 | 去掉 `imageData` 後沒有相片 | 先搬到 `image` 才刪除（AC11）；上線前先用測試資料確認 |
| 刪除優先規則 | 之前因時鐘問題「被救回」的酒，若雲端仍有舊墓碑，遷移後會被刪除 | 遷移時只對「墓碑時間晚於該酒 `addedAt`」的才生效；上線前在 Worker 加一次性統計（只記數量），估算受影響的酒款數目，結果告知用戶再決定 |
| 回退到舊版 | 舊版忽略 `_f`，回到整支酒 LWW；`imageData` 已刪的酒款仍有 `image`，不會失去相片 | 可直接回退，不需資料還原 |
| 單一 KV 值上限 | 加入 `_f` 令每支酒大約多 200–400 bytes | 去掉 `imageData` 節省的空間遠大於此（AC12） |
